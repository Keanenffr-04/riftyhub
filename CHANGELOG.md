# Changelog

## v19.0.0 – Language trends and saved-profile tests
- Language trends over time: a new **Language trends** panel on the Analytics tab (below Languages) shows which languages a developer started projects in, year by year, as a stacked bar chart. Switch between **Share** (each year adds up to 100%) and **Count**, and tick **Include forks** to count forks too (original repositories only by default). The five most used languages get their own colour, the same colours as the Languages panel, and everything else is grouped as **Other**. Years with no repository stay in the chart as empty bars, a legend names every colour, and **Show the numbers** opens a table (shares or counts, plus the year's total) for screen readers and exact values. It is built from the repositories already loaded, so it costs no extra GitHub request
- Honest about what it shows: each repository counts once, under its primary language, in the calendar year it was created. It shows where projects were started, not how much code was written each year or which languages a developer used in a year. Repositories with no detected language are left out and the note says how many
- More automated tests: new `tests/saved.test.ts` (22 cases) covers saved profiles and backups: note and collection-name cleaning, loading damaged or old profiles, search, collection and favourite filters, the three sorts, collection-name checks, merging imported profiles (existing data kept, notes never overwritten, favourites and collections combined, the 50-profile limit), and backups (round trip, rejected files, backups from before presets, pins and preferences, damaged content). New `tests/languageTrends.test.ts` (8 cases) covers the trends helper. The suite is now 83 cases
- Internal: `src/utils/languageTrends.ts` (`computeLanguageTrends()`, `yearShare()`), `LanguageTrendChart` in `Charts.tsx`, and `LanguageTrendsPanel` (loaded with the Analytics page, so the charting code is still downloaded only there). No new dependencies
- Verified: the 30 new test cases were compiled with TypeScript and run in the sandbox that prepared this version, on Node's test runner with a small stand-in for Vitest (no internet to install the real one); all passed. The type-check of the project showed no error in the new or changed files, but it is not a full pass: the React and Recharts packages are not installed there, so their errors remained. Not run: the real `npm test`, `npm run build`, and the screens. Please run `npm test` and `npm run build` and send any errors. Not checked: how the chart, legend and table look in the browser (light and dark)

## v18.0.0 – Instant commit search and more tests

If the refresh fails, the saved results stay with a note saying why and how old they are, and a **Try again** button re-runs the search. Not-found and invalid errors still show normally. The suite is now 53 cases
- Fix: `npm run build` failed on `vite.config.ts` with a plugin type mismatch (Vitest bundles its own copy of Vite). The test settings moved to a new `vitest.config.ts`, so `vite.config.ts` no longer touches Vitest. `npm test` behaves as before. This affected v15 to v17
- Internal: `peekCommitSearch()` and a shared search-string builder in the GitHub service (no change to what is sent to GitHub); `useCommitSearch` returns the `refreshing` and `stale` flags and a `retry`. No new dependencies
- Verified: nothing was run in the sandbox that prepared this version (no internet, no Vitest); the changed hook and service were type-checked in part (only errors from the missing React packages remained) and the new tests were reviewed by reading only. Please run `npm test` and `npm run build` and send any errors. Not checked: how the note looks in the commit explorer

## v16.0.0 – Per-repository activity
- Per-repository activity page: every repository card and table row (Repositories, Overview, Pinned) has an **Activity** link that opens `/u/<developer>/repos/<repository>`. The page shows the repository's name, description, stars, forks and last push with a link to GitHub, six activity tiles (public events, commits pushed, pull request events, issue events, reviews and comments, active days), a daily activity chart, and a timeline grouped by day with a filter by activity type and "Show more". It is built from the developer's own public events, so it costs no extra GitHub request when the Activity tab was already opened. The chart covers the same span as the developer's whole activity, so quiet repositories show their gaps. The page is addressable and shareable, has a breadcrumb back to Repositories, and its tab title reads "Activity of <repository> · <developer> · RiftyHub"
- Honest about what it shows: only the developer's own events from the last 90 days (at most 300 across all repositories) are available, so a repository with no events is explained as "nothing in the window GitHub shares", not "never active", and a very busy account's oldest days may be missing. An unknown repository name (renamed, deleted, or beyond the 300 repositories RiftyHub loads) shows a clear message with a link back
- Stale-while-revalidate extended: the Activity tab, the new repository page and the Compare page now also show saved data instantly and refresh it quietly (before, only the profile and repository list did). Compare shows saved data when every developer in the comparison is saved in this tab, refreshes any that are past their 10 minutes, and keeps the saved data with a note if a refresh fails. Commit search and the Recent activity comparison on Compare still load fresh as before
- Internal: the timeline moved into a shared `EventTimeline` component used by the Activity tab and the repository page (the Activity tab looks and behaves as before); `repoEvents()` and an optional start for `eventsByDay()` in `src/utils/activity.ts`; `peekUserEvents()` in the GitHub service; `RefreshNote` now takes any state that carries the refreshing and stale flags. No new dependencies
- Tests: 7 new cases (repository filtering, chart span, tab titles); the suite is now 38 cases, all passing in the sandbox that prepared this version, run with a small stand-in for Vitest built on Node's test runner (no internet to install the real one). Every changed file was syntax-checked. The full type-check (`npm run build`), the real `npm test` and the screens were not run. Please run `npm install`, `npm test` and `npm run build` and send any errors. Also not verified: that the v15 and v16 screens look right in the browser

## v15.0.0 – Instant revisits and automated tests
- Stale-while-revalidate: when you open a developer you have looked at earlier in the same browser tab, RiftyHub now shows the saved profile and repositories **immediately**, even if they are older than 10 minutes, and fetches a fresh copy quietly in the background. A small note says "Showing saved data while checking GitHub for updates…" and the page switches to the new data as soon as it arrives, without a loading screen. If the quiet refresh fails (rate limit, offline, GitHub problem, rejected token), the saved data stays on screen with a note saying why and how old it is, and a **Try again** button. A developer who no longer exists, or an invalid name, still shows the normal error instead of old data. Data that is still fresh (under 10 minutes) behaves exactly as before, **Refresh data** and **Try again** on an error still force a full reload, and data older than 24 hours is no longer shown
- Cache: entries now remember when they were stored and are kept for 24 hours after their normal 10-minute lifetime (still only in this tab's session storage, so closing the tab clears them). Cache entries from v14 are removed on start (the cache format changed). The Settings count and "Clear cached data" now include saved-but-stale entries, since those are also shown to you
- Automated tests: `npm test` runs a Vitest suite in `tests/` (31 cases) covering the cache (freshness, stale window, forced reload, de-duplication, clean-up, clearing), username validation, the comparison helpers (link parsing, lead tally, language overlap), pinned repositories and the repository search operators. `npm install` is needed once to download Vitest (new dev dependency; it is not part of the production build)
- Internal: new `peek()` in the cache and `peekUserData()` in the GitHub service (read stored data without a request); `useGitHubData` returns `refreshing` and `stale` states, shown by the new `RefreshNote` component. Other pages and hooks are unchanged
- Verified: the 31 tests were run in the sandbox that prepared this version, but with a small stand-in for Vitest built on Node's own test runner (the sandbox has no internet access to install the real one), and a syntax check of every changed file. The full type-check (`npm run build`), the real `npm test` and the screens were not run. Please run `npm install`, `npm test` and `npm run build` and send any errors
- Not covered: the stale-while-revalidate behaviour covers a developer's profile and repository list (shared by the Overview, Repositories and Analytics tabs). Compare, the Activity tab's events, commits and Saved profiles still wait for fresh data once the 10 minutes are over (see the backlog)

## v14.0.0 – Compare more developers and their activity
- Compare up to four developers: the Compare page now takes two to four usernames. Use **Add developer** for a third and fourth box and the ✕ to remove one. Everything adapts to the number of people: the summary says how many metrics each developer leads (a metric with no single leader is counted separately), the table highlights the highest value in each row (nothing is highlighted when everyone is equal, and a shared top spot highlights everyone who has it), and language overlap shows the languages all of them use, the ones some of them share, and the ones only one of them uses. Links keep working: two-developer links from earlier versions open exactly as before, and a link now holds up to four names (`?a=…&b=…&c=…&d=…`). A link with an invalid or repeated name explains what is wrong instead of showing nothing
- Compare selected on Saved profiles now works for two to four ticked profiles (the button shows how many)
- Side-by-side activity comparison: a new **Recent activity** section on Compare (button: "Compare recent activity") shows events per week for the last 13 weeks as a line chart, with a table of public events, commits pushed, pull requests, issues, reviews and comments, active days, average events per week and busiest week, and a collapsible table of the weekly numbers. Lines differ in colour and in dash pattern, so they can be told apart without relying on colour, and the colours follow the light and dark theme. It loads only when asked, because it costs up to 3 GitHub requests per developer (the button says how many), and the chart code is downloaded only then. If one developer's data cannot be loaded (for example a rate limit), the others are still compared and the problem is explained
- Honest about GitHub's limits: GitHub shares at most 300 public events from the last 90 days. For a very busy developer the oldest weeks are therefore cut off. These weeks are shown as gaps in the chart and "—" in the numbers (not as zero), are left out of their average, and a note says from which date the data starts. The oldest of the 13 weeks may also be slightly incomplete
- Internal: username validation moved to a small separate module (`src/utils/username.ts`, still exported from the GitHub service); the comparison and weekly-activity logic lives in `src/utils/compare.ts` and `src/utils/compareActivity.ts`. No new dependencies
- Verified with a throwaway script (not part of the repo): 19 cases covering link parsing (including blanks, @ signs, repeated names in different letter case, invalid names, more than four names, two-developer links from earlier versions), the lead tally (identical to the old two-developer rule for two people, shared top spots for three), language overlap for two and four developers, Monday-based week boundaries across daylight-saving changes, weekly counts, the 300-event cut-off handling and empty data; plus a syntax check of every changed file. The full type-check (`npm run build`) and the screens were not run in the sandbox that prepared this version

## v11.0.0 – Repository explorer
- Search operators: the Repositories search box now understands `stars:>100`, `forks:<=5`, `issues:0`, `stars:10..50`, `lang:python` (`lang:"jupyter notebook"`, `lang:none`), `topic:react`, `license:mit` (`license:none`), `is:fork` / `is:source` / `is:archived`, `pushed:>2024-06-01` and `created:2023` (a day, month, year or `from..to` range), `name:` and `desc:`. Put a minus in front to exclude (`-is:fork`). Plain words and quoted phrases work as before and can be mixed with operators. An operator with a value that can't be understood is listed as "not understood, so ignored" instead of silently matching nothing, and a collapsible "Search tips" panel explains each form
- Sortable table headers: click Repository, Stars, Forks or Updated to sort; click again to reverse. The active column shows its direction and is announced to screen readers (`aria-sort`)
- Saved filter presets: name and keep up to 20 searches (search text, filters and sort), apply them with one click, and delete them. The preset matching the current view is highlighted. Presets are included in backups and merged on import (existing names are kept)
- Repositories page defaults (Settings): choose the sort, direction, and whether forks or archived repositories are hidden when the page opens. Anything changed on the page wins, and shared links carry only what was changed, so the recipient's own defaults fill in the rest
- Data safety: stored presets and defaults are validated on load like all other stored data; older backups without presets import normally. No new dependencies
- Verified with a throwaway script (not part of the repo): 31 search cases (every operator, negation, ranges, invalid values, quoted phrases) and the address round trips with custom defaults. The build and the screens were not run in the sandbox that prepared this version

## v9.0.0 – Performance and reliability
- API and caching: repository pages now load in parallel (the profile's repository count says how many pages exist), repositories are slimmed to the fields the app uses (about 90% smaller in memory and storage), expired and old-format cache entries are removed on start, and the soonest-expiring entries are evicted when browser storage is full
- Requests: 15-second timeout, up to two automatic retries (with a short pause) for network failures and GitHub server errors, no retries for not-found or rate-limit errors, and no requests are sent once the quota is known to be used up (search keeps its own quota)
- Pagination and speed: Repositories shows 24 cards or 50 rows at a time with "Show more"; search waits 250 ms after typing before updating; Analytics and Activity (and the charting library) are lazy-loaded
- Reliability: error boundary so a crashing page shows a message with Reload and Home instead of a blank screen, offline banner, clearer messages for timeouts and GitHub server errors
- Accessibility: skip-to-content link, per-page tab titles, focus and scroll reset on page change, text lists behind every chart, 44 px touch targets on touch screens
- Responsiveness: filter controls stack full width on small phones
- New error kind "server" for GitHub 5xx responses. No new dependencies
- Adapted from roadmap: loading skeletons, focus styles and reduced-motion support already existed, so v9 builds on them
